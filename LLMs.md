# AI Coding Assistants

This document provides guidance for AI tools and developers using AI
assistance when contributing to Tether.

AI tools helping with Tether development should follow the standard project
development process and repository documentation, including:

- `CONTRIBUTING.md`
- `SECURITY.md`
- Relevant documentation under `docs/`

AI assistants MUST read the relevant documentation for the task before making
changes. Do not rely only on isolated sections found through keyword search.

## Licensing and Legal Requirements

All contributions must comply with Tether's licensing requirements.

- Tether is licensed under the GNU Affero General Public License v3.
- New code must be compatible with the project's license.
- Appropriate SPDX license identifiers should be used where the project
  requires them.
- Third-party code must have compatible licensing and must be properly
  attributed where required.
- AI tools must not introduce code of unknown provenance.
- AI-generated code must not be assumed to be license-safe simply because it
  was generated by an AI system.

The human contributor is responsible for verifying that submitted code
complies with all applicable licensing requirements.

## Human Responsibility

AI agents MUST NOT represent themselves as the legal or accountable author of
a contribution.

The human submitter is responsible for:

- Reviewing all AI-generated or AI-modified code.
- Understanding the submitted changes.
- Ensuring compliance with licensing requirements.
- Verifying technical correctness.
- Verifying security-sensitive behavior.
- Running or reviewing the relevant tests.
- Taking full responsibility for the contribution.

AI assistants must never claim that human review occurred unless it actually
did.

## Attribution

When AI tools materially contribute to a change, the contribution should
disclose that assistance.

For commits, the following trailer may be used:

```text
Assisted-by: LLM
```

A more specific form may also be used:

```text
Assisted-by: LLM Codex
Assisted-by: LLM Claude Code
Assisted-by: LLM GitHub Copilot
```

Basic development tools such as Git, Go, Java, compilers, editors, and build
systems should not be listed.

AI assistants MUST NOT invent attribution or claim assistance from tools that
were not actually used.

## Repository and Architecture Requirements

Before making changes, AI assistants MUST inspect the relevant existing code
and preserve Tether's architectural boundaries unless the requested task
explicitly requires an architectural change.

Tether consists primarily of:

### Orchestrator

The Orchestrator is responsible for:

- Discovering and managing approved machines.
- Pairing with Agents.
- Coordinating Agents.
- Evaluating available resources.
- Selecting model placement.
- Managing model workers.
- Exposing Tether's OpenAI-compatible API.

### Agent

The Agent is responsible for:

- Managing resources on its local machine.
- Reporting available resources and status.
- Managing locally configured `ggml-rpc-server` instances.
- Starting and stopping approved local processes when instructed by the
  Orchestrator.

Agents are not responsible for global scheduling decisions.

### llama.cpp

`llama.cpp` performs model inference.

Tether integrates with `llama.cpp` and its RPC functionality rather than
reimplementing the inference engine.

AI assistants MUST NOT move responsibilities between these components without
a clear architectural reason.

## Security-Critical Areas

The following areas must be treated as security-sensitive:

- Device pairing.
- Authentication.
- Authorization.
- mTLS.
- Certificate generation.
- Certificate storage.
- Certificate validation.
- Certificate pinning.
- API authentication.
- Agent control.
- Remote process execution.
- Network listeners.
- Remote RPC connectivity.
- Configuration containing credentials or secrets.
- Process arguments passed to `llama.cpp`, `llama-server`, or
  `ggml-rpc-server`.

AI assistants MUST NOT:

- Disable TLS or certificate validation for convenience.
- Weaken authentication or authorization checks to resolve unrelated bugs.
- Introduce insecure fallback authentication.
- Log secrets, authentication tokens, passwords, private keys, or pairing
  secrets.
- Store secrets in source code.
- Introduce arbitrary command execution where a constrained interface is
  sufficient.
- Expose services on additional network interfaces without considering the
  security impact.
- Construct shell commands from untrusted input where direct argument passing
  is possible.

Security checks should fail closed where practical.

## Handling Secrets and Sensitive Data

AI assistants MUST NOT place any of the following into source code,
documentation, tests, examples, logs, commits, or issue reports:

- Private keys.
- API keys.
- Passwords.
- Authentication tokens.
- Personal access tokens.
- Pairing secrets.
- Private certificates or private certificate material.
- User credentials.
- Sensitive personal data.

Use placeholders in documentation and examples.

Example:

```text
TETHER_API_TOKEN=<your-token>
```

Never reproduce secrets found in:

- Terminal output.
- Environment variables.
- Configuration files.
- `.env` files.
- Logs.
- Issue reports.
- User prompts.

## Network Code

Tether is a distributed system.

AI assistants modifying network-facing code MUST consider:

- Connection failure.
- Timeouts.
- Partial reads and writes.
- Malformed input.
- Disconnects.
- Reconnection.
- Duplicate requests.
- Partial Agent failure.
- Unavailable Agents.
- Stale state.
- Authentication failure.

Network input must be validated.

Do not assume an Agent is available because it was previously discovered.

Do not assume Tailnet membership alone replaces Tether's own authentication
and authorization mechanisms.

## llama.cpp and ggml-rpc Integration

When modifying integration with `llama.cpp` or `ggml-rpc`, AI assistants MUST:

- Verify that command-line arguments actually exist.
- Verify behavior against the relevant supported version.
- Avoid inventing flags, endpoints, or capabilities.
- Preserve useful stderr and stdout output for diagnostics.
- Handle process startup failures.
- Distinguish process creation from actual service readiness.
- Use readiness checks where appropriate.
- Consider upstream version differences when relevant.

If a bug belongs entirely to an upstream project, the AI assistant should
identify that distinction instead of silently modifying Tether around it.

## Procedure for Finding and Fixing Bugs

When an AI assistant is used to find and fix bugs, it MUST follow at least
these steps:

1. Read the relevant project documentation and the code involved in the
   requested task before making changes.

2. Record or identify the current commit or repository state where practical,
   so the change can be associated with a specific code state.

3. Identify the suspected bug and verify that it is real.

4. For non-trivial bugs, create or identify a reproducible case where
   practical. Do not continue treating a suspected issue as confirmed if the
   available evidence shows that the behavior is correct.

5. Determine the underlying cause rather than only suppressing the visible
   symptom.

6. Implement the smallest reasonable fix that addresses the root cause.

7. Do not perform unrelated refactoring, formatting, dependency upgrades, or
   cleanup as part of the fix unless required.

8. Build and test the affected component.

9. Re-run the reproducer or equivalent validation and confirm that the issue is
   resolved.

10. Ensure the fix does not introduce new warnings, test failures, regressions,
    or obvious security issues.

11. Add or update tests where practical, especially for regressions.

12. Review the final diff for unrelated changes, accidental secrets, and
    unintended behavior changes.

13. Clearly state what was and was not verified.

14. If the change could not be built, tested, reproduced, or fully verified,
    say so explicitly.

AI assistants MUST NOT claim that a bug is fixed unless the available evidence
supports that claim.

## Security Bug Classification

Before treating a bug as a security vulnerability, AI assistants should review:

- `SECURITY.md`

The assistant should determine whether the issue appears to cross a documented
security boundary or create a meaningful security impact.

AI assistants MUST NOT publicly disclose security-sensitive details when doing
so would expose users before a fix is available.

AI assistants should not independently publish, report, or disclose a
vulnerability to third parties unless explicitly instructed by the human
maintainer.

## Testing Requirements

AI assistants MUST run relevant tests when the environment permits it.

At minimum:

- Test the package or component that changed.
- Run broader tests when shared infrastructure is affected.
- Add regression tests for bug fixes where practical.
- Add tests for new behavior where practical.

Security-sensitive changes should include negative tests where reasonable.

Examples include confirming that:

- Invalid credentials are rejected.
- Invalid certificates are rejected.
- Unauthorized Agents cannot perform restricted actions.
- Malformed network requests are handled safely.
- Invalid configuration does not silently weaken security.

AI assistants MUST NOT modify tests merely to make an incorrect implementation
pass.

## Error Handling

Errors should contain enough context to diagnose failures without exposing
sensitive information.

Prefer:

```text
failed to connect to agent "node-2": TLS handshake failed
```

over:

```text
connection failed
```

Do not include:

- Passwords.
- Tokens.
- Private keys.
- Pairing secrets.
- Sensitive configuration values.

Errors must not be silently ignored unless the failure is explicitly
non-critical and that behavior is intentional.

## Logging

Logs should help diagnose distributed behavior.

Useful context may include:

- Component.
- Agent identifier.
- Operation.
- Worker identifier.
- Model identifier.
- Failure stage.

Do not log:

- Authentication tokens.
- Pairing secrets.
- Passwords.
- Private keys.
- Full sensitive configuration.
- User prompt contents unless explicitly required and handled appropriately.

## Concurrency

When modifying concurrent code, AI assistants MUST consider:

- Data races.
- Cancellation.
- Shutdown behavior.
- Goroutine or thread leaks.
- Process leaks.
- Socket leaks.
- File descriptor leaks.
- Deadlocks.
- Lock ordering.
- Work occurring while locks are held.
- Operations completing in an unexpected order.

Do not assume concurrent operations complete in a particular order unless that
ordering is explicitly guaranteed.

## Process Management

When Tether launches external processes, AI assistants MUST ensure that:

- Process lifecycle is tracked.
- Startup failures are detected.
- Unexpected exits are handled.
- Child processes are cleaned up where appropriate.
- Shutdown behavior is deterministic where practical.
- Command arguments are validated.
- Untrusted values are not interpolated into shell commands.

Avoid invoking a shell when direct process argument passing is sufficient.

## API Compatibility

Tether exposes an OpenAI-compatible API.

When modifying API behavior:

- Preserve existing compatibility where practical.
- Validate incoming requests.
- Use appropriate HTTP status codes.
- Return structured errors.
- Avoid silently changing response formats.
- Document intentional incompatibilities.
- Avoid claiming compatibility with endpoints or behavior that Tether does not
  actually support.

Breaking API changes must be deliberate and documented.

## Dependencies

Before adding a dependency, AI assistants MUST determine whether:

1. The standard library already provides the required functionality.
2. An existing dependency already provides it.
3. The additional dependency is justified.
4. The dependency is actively maintained.
5. Its license is compatible with Tether.
6. Its security and maintenance cost is acceptable.

Do not add large dependencies for trivial functionality.

## Documentation

Documentation MUST be updated when a change affects:

- Public APIs.
- CLI arguments.
- Configuration.
- Installation.
- Network behavior.
- Security behavior.
- Architecture.
- User-visible behavior.
- Supported deployment behavior.

Do not document features that are not actually implemented.

## Breaking Changes

AI assistants MUST NOT introduce breaking changes casually.

If a breaking change is necessary:

1. Identify it explicitly.
2. Explain why it is required.
3. Update affected documentation.
4. Update relevant tests.
5. Document migration requirements where applicable.

## Git and Repository Hygiene

AI assistants MUST keep changes focused.

Do not:

- Rewrite unrelated history.
- Force-push.
- Delete branches.
- Modify release tags.
- Commit local configuration.
- Commit models or large generated artifacts unless explicitly requested.
- Commit build output unless the project intentionally tracks it.
- Commit secrets.
- Reformat unrelated files.
- Rename unrelated files.
- Upgrade unrelated dependencies.

Do not destroy uncommitted human work.

## Destructive Operations

AI assistants MUST NOT run destructive commands without explicit human
authorization.

Examples include:

```text
rm -rf
git reset --hard
git clean -fdx
git push --force
git branch -D
```

Prefer reversible operations wherever possible.

## Scope Discipline

AI assistants should only modify files necessary for the requested task.

Do not perform unrelated:

- Refactoring.
- Formatting.
- Cleanup.
- Dependency upgrades.
- File renaming.
- Architectural redesign.
- API redesign.

If unrelated problems are discovered, report them separately.

## Before Completing a Task

Before considering a task complete, an AI assistant MUST:

1. Review the final diff.
2. Confirm that the requested behavior was implemented.
3. Run relevant tests where possible.
4. Check for accidental secrets.
5. Check for unrelated changes.
6. Review error paths.
7. Consider security implications.
8. Update relevant documentation.
9. State any tests or checks that were not performed.
10. State any assumptions that remain unverified.

AI assistants MUST NEVER:

- Claim tests passed when they were not run.
- Claim code was built when it was not built.
- Claim behavior was verified when it was only inferred.
- Fabricate test output.
- Fabricate repository state.
- Fabricate documentation or API behavior.
- Invent upstream features or command-line flags.
